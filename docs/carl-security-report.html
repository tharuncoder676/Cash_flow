Website security · Protection report

How the site is protected, and what only you can secure

What was already in place, what we have added, how each protection was tested, and the handful of steps that sit with your own accounts.

Dear Sir,

This document follows our build progress report (FN-CFM-002) and covers the security of the Cash Flow Mastery website. Before adding anything, we audited what the site already did, so that the work below targets real gaps rather than a generic checklist.

Every protection listed as tested was checked against the running site, not assumed from the code. Where something could not be tested yet — usually because it depends on your Stripe account being connected — we say so plainly.

The short version: the website itself is now well protected. The remaining risk sits in accounts only you control — the database that will hold customer details, your Stripe settings, and sign-in security on the services the site runs on.

01

Already in place

Verified before this work

These were built in from the start. We re-checked each one during the security audit rather than relying on the original build notes.

A1

Encrypted connection with strict HTTPS

In place

Every page is served over HTTPS, and browsers are instructed never to connect to the site any other way for two years.

A2

Payment confirmation cannot be faked

In place

A place on the course is granted only when Stripe itself confirms a payment, and only once the money is marked as paid. Messages claiming to be from Stripe are rejected unless they carry Stripe’s signature, and a repeated confirmation can never book a second seat.

A3

Prices are set by the server

In place

The price is calculated on our side from the number of places sold. A visitor cannot edit the amount in their browser to pay less.

A4

No secret keys exposed

In place

Stripe’s secret key and the stored customer details are excluded from the code repository. Only Stripe’s publishable key, which is designed to be public, is visible in the site.

A5

No known vulnerable software

In place

An automated audit of every third-party package the site uses found zero known vulnerabilities.

A6

Safe links to outside websites

In place

All nine links that open another site in a new tab, such as WhatsApp and LinkedIn, are set so that site cannot take control of this one.

A7

Forms and checkout accept only what they expect

In place

The form and checkout endpoints reject every request type except the one they use, validate email addresses, and limit the length of names and company names.

A8

The confirmation page cannot grant access

In place

The page shown after paying only reports what Stripe says. Opening it without paying shows an error, never a place on the course.

Two limits we want you to know about

The submission limit (S4) slows abuse rather than stopping it outright. The site runs on many small servers at once, and each keeps its own count. A determined attacker spreading requests across them can exceed the limit. A firm limit needs a shared service — see item N2 below.

The code-source rule (S3) keeps the site fast. The strictest version forces every page to be rebuilt on each visit, making the site slower and costlier to run. We chose a version that keeps pages pre-built while still blocking embedding, foreign form submissions and unexpected code sources.

03

What we need from you

6 items

These cannot be done in code, because each depends on an account or a decision that belongs to you. Items N1 to N3 should be settled before the site takes its first real payment.

N1 · Before launch

A proper database for customer details

Needs you

Enquiries and enrolments are currently written to a simple file. That is fine for testing, but it is not suitable for personal data, and the live hosting does not keep files permanently — so on the live site, form submissions will not be saved at all. We recommend Supabase, which has a free tier. Please create an account, or approve us to set one up in your name.

N2 · Before launch

A firm limit on repeated submissions

Needs you

To make the submission limit hold across every server, either upgrade the hosting to Vercel Pro, which includes firewall rules, or create a free Upstash account. We have built the site so either can be connected in minutes.

N3 · Before launch

Stripe account settings

Needs you

Three things in your Stripe dashboard: create a restricted API key limited to what the site needs, instead of the all-powerful secret key; switch on Radar fraud rules; and share test-mode keys so we can confirm the refund protection (S10) and checkout checks (S11) end to end.

N4

Two-step sign-in on every account

Needs you

Please turn on two-factor authentication for Vercel, Stripe, your domain registrar and the email account used for the site. A stolen password on any of these would bypass every protection above.

N5

Protect your email domain from impersonation

Needs you

Without SPF, DKIM and DMARC records, anyone can send email that appears to come from @independentadvisors.ai — for example, a fake payment request to a prospective student. These are set in your domain’s DNS by whoever manages it. We are happy to provide the exact records.

N6

Confirm the security contact

Needs you

The security contact file currently lists carl@independentadvisors.ai and the domain cashflowmastery.co. Please confirm the address reports should go to, and the final domain for the course site.
